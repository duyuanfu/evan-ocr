## Context

Evan 拥有毫秒级屏幕捕获、矢量标注、单字符就地修改与双 OCR 引擎。用户在提取屏幕文字后，高频需求是将识别出的文本（尤其英文文献、报错日志、日韩文档或专业术语）快速翻译为目标语言。
然而，离线神经机器翻译（NMT）模型权重（如 MarianMT / OPUS-MT / CTranslate2）通常体积在 50MB~300MB+ 之间。若将离线模型直接内置进主安装包，会导致软件体积从 20MB 骤增至数百兆，严重违背 Evan“极简、轻量、秒启”的定位。
因此，采用**插件化解耦架构（Plugin-based Translation Architecture）**成为最佳技术方案：主程序保持纯净零膨胀，提供统一翻译接口与 UI 对照视口；离线翻译作为可选独立插件包分发。

## Goals / Non-Goals

**Goals:**
- **主程序零体积膨胀**：主程序仅集成翻译接口契约与交互视图，0MB 额外模型体积绑定。
- **开放可插拔架构 (`ITranslator` & `TranslationPluginManager`)**：
  - 支持探测 `plugins/translation/` 独立扩展目录；
  - 采用无崩溃风险的进程隔离 IPC / JSON 通信或标准扩展驱动，隔离崩溃风险与内存开销；
  - 自动检测已安装模型并列出支持的互译语言对（中英、英中、日中等）。
- **双轨运行模式（离线插件 + 在线备选）**：
  - 用户未安装离线包时：提供轻量内置在线直连驱动，开箱即用，并提供离线包一键下载指引；
  - 用户解压离线包后：自动点亮“100% 纯本地离线翻译”引擎，彻底免联网且保证数据隐私。
- **现代化多栏对照交互升级 (`OcrResultDialog`)**：
  - 在现有「原图对照 + 提取文字」左右视图中，提供可折叠展开的「🌐 译文对照」分栏；
  - 支持语言下拉切换（自动推测源语言）、段落合并格式继承与独立一键复制。

**Non-Goals:**
- 本项目 Git 仓库绝不直接提交上百兆的深度学习翻译模型权重。
- 不引入重型 Python 全套运行时环境，插件优先采用轻量编译型 C++/Rust/ONNX 推理二进制。

## Decisions

### 1. 插件技术路线：进程隔离 IPC 协议驱动
- **决定**：借鉴项目中已经成熟验证的 `RapidOCR` 架构模式，`TranslationPluginManager` 通过探测 `plugins/translation/` 目录中的可执行引擎（如 `translator-engine.exe` 或 `ctranslate2-runner.exe`）及模型文件夹，通过标准进程输入输出进行 JSON / 文本通信。
- **对比**：若采用 `QPluginLoader` 动态链接库，Windows 下对 MSVC 编译器小版本、Qt 二进制 ABI 有严格苛刻的匹配要求，任何编译微差都会导致主程序直接 Crash。进程隔离方案具备 100% 内存安全隔离、崩溃不牵连主程序、易于跨语言打包的绝对优势。

### 2. 语种自动嗅探与段落继承
- **决定**：
  - 基于已有的 `CharFontAnalyzer` 与 OCR 文本特征进行简单高效的语种自动嗅探（若含汉字比例超过 30% 默认判定为中文并推荐译为英文；若为拉丁字母则默认推荐译为中文）；
  - 翻译输入直接绑定 `OcrResultDialog` 中的 `¶ 合并段落` 和 `␣ 清除空格` 过滤器，确保送入翻译引擎的是连贯自然的长句，显著提升翻译通顺度。

### 3. UI 布局：可展开的三栏 / 下拉抽屉式对照设计
- **决定**：在 `OcrResultDialog` 右侧文字区域下方设计可自适应展开的翻译卡片区，配备源语言、目标语言选择下拉菜单、翻译触发按钮和独立 `📋 复制译文` 按钮，保持整体 Fluent Light 极简现代风格。

## Risks / Trade-offs

- **[模型初次加载耗时风险]**：离线 NMT 模型首次冷启动加载进内存可能需要数百毫秒。
  - *缓解措施*：所有翻译请求在 `QThreadPool` 后台工作线程异步派发，UI 呈现非阻塞微型加载动画，完成后主线程平滑刷新。
- **[未安装离线插件时的用户体验落差]**：
  - *缓解措施*：当未检测到离线插件时，不直接弹窗报错，而是自动平滑启用无依赖在线翻译兜底，并友好提示“已使用在线引擎，如需纯离线可前往下载离线扩展包”。
